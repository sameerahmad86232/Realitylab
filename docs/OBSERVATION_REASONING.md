# Phase 4 — review an observation without turning it into a fact

## Implemented workflow

In a generated or recorded build dossier, expand a practical step's observation journal. Record an outcome and actual notes, then choose **Draft a question about this result**. Drafting is local and needs no provider consent or request. The question editor receives a visible attachment containing the full original instruction, model prediction, notes, outcome, report timestamp, scan ID and lesson/step reference. Notes are not silently shortened to fit the 600-character question field.

Inspect the attachment and edit the question. Consent and **Ask Meta about this scan** are still required to send it. Only that explicit action makes one normal learning request; no hidden verifier, extra model call or automatic retry is added. No photos are resent. If the journal changes after drafting, sending is blocked until the attachment is updated or removed. Removing it clears the draft question. Failed requests retain the draft for review/retry. Successful replies retain their exact attached snapshot in the tab cache and learning export.

The context is client-supplied. Matching IDs and schema checks prevent accidental cross-scan/step mixing; they do not authenticate a physical event, prove a lesson was generated by the provider or establish independent truth. The server has no persistent record that can attest to those facts.

## Model reasoning and output

The prompt separates three layers: source-photo analysis (itself model-generated), a proposed craft instruction/prediction, and an unverified reported outcome. It asks the model to challenge physically questionable predictions instead of automatically blaming the user, suggest 1–3 possible explanations and distinguish each with a safe passive observation on the separate craft model. No original-object modifications or powered tests are introduced.

An attached question requires a bounded `observation_review` when the model returns a ready answer. That section must echo the attached lesson UUID and step index. Allowed statuses are **consistent with report**, **questionable**, and **insufficient evidence**; there is no “verified” result. Hypotheses, distinguishing observations and limits are rendered separately. Ordinary questions cannot receive an unsolicited review section. Local observational refusals remain valid without a review.

The full snapshot is checked for known disallowed topics before inference. Source/component mismatch rejects before a paid call; missing or mismatched model review data returns a sanitized error with no substitute. The frontend repeats lesson/reference checks before rendering. These guards check structure and association, not mechanical truth or the quality of the prose.

## Validation

Unit/API tests cover exact full-note preservation, unsupported/unperformed attachments, cross-source rejection, step/lesson mismatch, missing structured replies, forbidden verified statuses, a local boundary without inference and one-call context forwarding. Browser tests cover local drafting, focus, consent, full attachment preview, stale/update/remove behavior, structured interpretation, snapshot exports, tab navigation, mobile width and automated accessibility. Test observations and model responses are explicitly synthetic fixtures, never physical trials.

An optional one-call real integration probe is available:

```sh
node --use-env-proxy --use-system-ca scripts/validate-observation-review.mjs --live
```

It submits a clearly tagged **hypothetical-test** report about the recorded fan craft proposal. This uses provider credits, makes at most one learning request, performs no physical experiment and claims no improvement in accuracy. The response, request, source revision, timing and usage are saved in a fresh `/tmp/artifacts/observation-reasoning/…` directory. It does not invent a user observation or independently grade the model's answer.

## Remaining evidence gate

The software now connects an observation to source-grounded follow-up reasoning. A before/after evaluation on independent held-out cases, real human review and physical trial evidence are still missing. Successful schema validation or a plausible Meta response does not close those Phase 2–4 gates or establish a causal correctness gain. The Phase 3 result file remains empty until an actual trial is supplied.
